# 智慧點餐小幫手

一個給小型單位用的午餐訂餐系統：服務對象在平板上點一點，就能幫每個人記下今天訂什麼、多少錢、付了沒。

它會自動把全部人的訂單合併成一張「打電話給店家用的小抄」，也能列印當日報表。

整套只有一個 `index.html` 檔案，不用安裝任何東西，丟到免費的網頁空間就能跑。

## 為什麼公開釋出

因為我們想擴散的不是這幾千行程式，是「讓服務對象自己做決定」的機會。

以前訂餐是工作人員問一輪、寫在紙上。現在是把平板遞過去，他自己滑、自己選、自己按下確認，然後在畫面上看見「我今天訂了什麼」。同一件事，主詞從工作人員換成了他本人。這個換位很小，但它每天都發生一次。

我們有幸做出了一些雛型架構，AI 時代來臨，應該讓服務對象有機會更多的參與與自主，所以我們選擇公開釋出。你的單位如果也在用紙本問一輪，把這份檔案拿去改成你們的樣子；唯一不行的是拿去賣，授權細節見文末。

## 不接 issue、不接 PR，但這裡有一把鑰匙

我們沒有維護人力。這套系統是白永恩基金會台南辦公室鄭智文主任為了解決小作所服務上遇到的痛點做的。所以這個倉庫不會有人看 issue，也不會有人審 PR。你開了，它就會一直躺在那裡沒有回音，與其讓你等，不如現在講清楚。

**把整個 `index.html` 丟給你的 AI（ChatGPT、Claude、Gemini 都可以），告訴它你要改什麼。** 它讀得懂。我們刻意把這個檔案切成 25 個有名字的區塊，就是為了這件事。在編輯器裡搜 `// 【` 就會跳到每一個區塊，檔案最上面還附了一張區塊地圖。你不必看懂程式，只要能指出「哪裡不對」「我想要什麼」，AI 就能幫你找到位置。

三個可以直接複製去問的例子：

```
這是一個單檔的 React 網頁（index.html），檔案開頭有區塊地圖。
我要把工坊改成三個：id 分別是 a、b、c，名稱是「甲工坊」「乙工坊」「丙工坊」。
請告訴我要改哪些地方，並給我改好的完整區塊。
```

```
這是一個單檔的 React 網頁（index.html）。
現在每個人的餐費補貼是固定金額，我想改成「不同身分的人補貼不同」。
請先告訴我這樣改會動到哪些地方、有什麼風險，我確認後再給我程式碼。
```

```
這是一個單檔的 React 網頁（index.html）。
列印出來的報表我想加一欄「備註」。
請只改列印那個區塊，其他不要動，並附上改動前後的對照。
```

一個小提醒：AI 有時候會「順手」改掉你沒要它改的地方。請它「只改某個區塊、其他不要動」，改完存檔前先在瀏覽器開一次確認畫面正常。改壞了也不要緊，把原始檔案重新下載一份就好。

## 五分鐘跑起來

這套系統的資料放在 Google 的 Firebase（免費額度對一個小單位綽綽有餘）。以下六步做完就能用。

### 1. 開一個 Firebase 專案

到 <https://console.firebase.google.com> 用 Google 帳號登入，按「建立專案」，取個名字（例如 `my-lunch`），Google Analytics 可以不開。

### 2. 開 Firestore 與 Authentication

- 左側選單 →「Firestore Database」→「建立資料庫」→ 位置選離你近的（例如 `asia-east1`）→ 模式先選「正式版」（規則等一下會貼）
- 左側選單 →「Authentication」→「開始使用」→ 在「Sign-in method」分頁把 **電子郵件/密碼** 設為啟用
- 同一頁的 **匿名** 請保持停用

### 3. 建四個帳號

還在 Authentication，切到「Users」分頁，按「新增使用者」建立這四個：

| 帳號 | 這是誰的密碼 |
|---|---|
| `sunny@lunch.local` | 陽光工坊的登入 PIN |
| `river@lunch.local` | 河岸工坊的登入 PIN |
| `admin@lunch.local` | 管理員密碼（改菜單、改排程） |
| `sysadmin@lunch.local` | 系統管理員主密碼（新增或停用單位） |

**這不是真的信箱。** Firebase 規定帳號要長成 email 的樣子，所以我們給它一個 email 形狀的名字就好；`.local` 是網路標準保留給區網用的假網域，不可能被別人註冊，也不會有人寄信到那裡。

`sunny`、`river` 這兩個前綴要跟你的單位代號一致（見下一節「改成你們的樣子」）。有幾個單位就建幾個。密碼建議用純數字，因為登入畫面是一個計算機風格的數字鍵盤。

### 4. 貼上你的 Firebase 設定值

Firebase Console → 專案設定（齒輪）→ 一般 → 捲到最下面「你的應用程式」→ 如果還沒有網頁應用程式就按 `</>` 加一個 → 它會給你一段設定值。

打開 `index.html`，搜尋 `YOUR_API_KEY`，把這六欄換成 Console 給你的值：

```js
const firebaseConfig = {
  apiKey: "YOUR_API_KEY",
  authDomain: "YOUR_PROJECT_ID.firebaseapp.com",
  projectId: "YOUR_PROJECT_ID",
  storageBucket: "YOUR_PROJECT_ID.firebasestorage.app",
  messagingSenderId: "YOUR_SENDER_ID",
  appId: "YOUR_APP_ID"
};
```

（這六個值不是密碼，公開在網頁裡是 Firebase 的正常用法。真正擋人的是下一步的規則。）

### 5. 貼上安全規則

打開本專案的 `firestore.rules`，把整份內容複製起來 → Firebase Console → Firestore Database →「規則」分頁 → 全選貼上 → 按「發布」。

**這步不能跳過。** 沒發布規則的資料庫，全世界都能讀寫你的資料。

### 6. 丟到網路上

最簡單的方式是 Netlify（免費）：到 <https://app.netlify.com/drop>，把整個資料夾（`index.html` 加上 `assets/`）拖進去，幾秒後就會給你一個網址。

用平板打開那個網址，選單位、輸入密碼，就開始了。

## 改成你們的樣子

### 改單位代號與名稱

範例附的是兩個假單位：`sunny`（陽光工坊）與 `river`（河岸工坊）。**代號**（id）是英文小寫，程式內部用；**名稱**（label）是中文，畫面上顯示。

代號會出現在四個地方，改的時候四處都要對得上：

| 出現在哪 | 怎麼改 |
|---|---|
| `index.html` 的 `WORKSHOPS_FALLBACK`（搜 `// 【工坊備用資料】`） | 直接改 `id` 與 `label` |
| 網址參數 `?workshop=sunny` | 做捷徑或書籤時用得到，換代號就換這裡 |
| Firebase Console 的帳號名前綴 `sunny@lunch.local` | 建帳號時就要用新代號 |
| Firestore 資料庫 `units` 集合裡的文件 | 進系統後用「系統管理面板」新增或修改，不必手動改資料庫 |

四處沒對上時，登入畫面只會說「密碼錯誤」，不會告訴你這個帳號根本不存在。遇到怎麼打都登不進去，先回頭把上面四處核對一遍。

正式上線後，單位清單是從 Firestore 的 `units` 集合讀的；`WORKSHOPS_FALLBACK` 只是「資料庫整個讀不到時」的備胎。所以實務上：先用 sysadmin 密碼進系統管理面板把單位建好，`WORKSHOPS_FALLBACK` 再改成同樣的內容當備援。

### 改顏色

主色是橘色 `#E8750A`。搜 `brand:` 會找到 Tailwind 的色彩設定（`DEFAULT` 主色、`light` 淺底、`muted` 中間調、`dark` 深色），改這四個值就能整體換色。每個單位卡片還有自己的 `color` 欄位，在系統管理面板裡可以各別設定。

### 放上你們的 logo

公開版把原本的兩張機構 logo 拿掉了（我們的商標不能給別人用）。要放回去，圖檔放進 `assets/`，然後在這兩個位置插回一個 `<img>`：

1. **工坊選擇頁**：搜 `// 【畫面：工坊選擇與登入頁】`，在「智慧點餐系統」那個標題區塊上方
2. **主畫面頁首**：搜 `左側原為機構 logo`，那行註解就標在原本的位置

沒有 logo 也可以直接找 AI 生一張。可以複製這段去問：

```
請幫我設計一個社福單位的 logo，用途是放在午餐訂餐系統的頁首。
風格：簡潔扁平、線條乾淨，不要有文字。
主題：一碗飯加一雙筷子，或是一個手掌捧著碗的意象。
主色：橘色 #E8750A，背景透明。
輸出：正方形 PNG，去背。
```

生好之後存成 `assets/logo.png`，插回位置的程式碼長這樣（高度自己調）：

```jsx
<img src="assets/logo.png" alt="單位標誌" style={{ height: '48px' }} />
```

### 換字型

標題用的是「清松手寫體2」。為了不讓網頁變肥，我們只把用得到的 13 個字（`陽光工坊健康站河岸智慧點餐`）打包成 `assets/JasonHandwriting2-subset.woff2`，整個檔案只有 6KB。

代價是：**你換成自己的單位名之後，那幾個字不在包裡，標題會自動退回 Noto Serif TC**（版面不會壞，只是手寫的味道沒了）。

想保留手寫體，就要用你自己的字重新打包一次。這件事的工具不在這個倉庫裡，最省事的做法是把下面這段丟給你的 AI：

```
我有一個 woff2 網頁字型檔，想用 Python 的 fonttools 裡的 pyftsubset 重新做子集化，
只保留這幾個字：「（把你的單位名和標題文字貼在這裡）」。
請給我完整的安裝指令和執行指令，輸出格式要 woff2。
```

做好的檔案覆蓋 `assets/JasonHandwriting2-subset.woff2` 就好，`index.html` 不用改。也請順手更新一下 `index.html` 裡 `@font-face` 上方那行說明現在包了哪些字。

#### 想換成別的字型

手寫體只是我們的選擇，不是規定。你可以換成任何一套字型，做法一樣是把需求丟給 AI，但換之前先想過這四件事：

1. **授權**：網路上下載得到不等於可以放進你的網站散布。Google Fonts 上的字型全部可以用；標 SIL OFL 或 Apache 授權的可以用；買來的商用字型多半不行，要看授權書有沒有寫「網頁嵌入」。拿不準就問 AI「這套字型的授權可不可以嵌進公開的網站」，並把授權全文貼給它看。
2. **檔案大小**：一套完整的中文字型通常 5 到 20 MB，直接放進去會讓網頁在 iPad 上開很久。要嘛像我們一樣只打包用到的字，要嘛改用 Google Fonts 線上載入（不用放檔案，但沒有網路時會退回備用字型）。
3. **好不好讀**：這個標題是給服務對象和工作人員看的，不是給設計師看的。手寫體、圓體、藝術字在大字級當標題還可以，菜單和人名請維持一般黑體或明體。換完之後請一位服務對象看一眼，比任何設計原則都準。
4. **備用字型要留著**：`@font-face` 後面的 `'Noto Serif TC', serif` 是安全網，字型檔壞了或字不在包裡，版面才不會開天窗。叫 AI 改的時候，明確說「備用字型鏈不要動」。

可以直接複製去問的一段：

```
這是一個單檔 HTML 的點餐系統，標題目前用一套子集化的手寫體（@font-face 載入 assets/ 裡的 woff2）。
我想把標題換成「（字型名稱）」。請先告訴我：這套字型的授權能不能嵌進公開網站、完整檔案大概多大、
要不要子集化。確認後再給我要改的程式碼，備用字型鏈 'Noto Serif TC', serif 不要動。
```

（不想處理字型的話，把 `@font-face` 整段刪掉也完全沒問題，標題就一律走 Noto Serif TC。）

## 這東西是怎麼組起來的

### 為什麼是一個檔案

整套系統就是 `index.html` 這一個檔案，加上 `assets/` 裡的字型和一張圖示。沒有 `npm install`、沒有編譯步驟、沒有建置流程。

**好處**：任何人下載下來、用記事本就能改；丟到任何空間都能跑；十年後想改的人不會卡在「裝不起舊版工具」。對沒有工程人力的單位，這是最能活得久的形態。

**代價**：

- 畫面用 React 寫，但沒有事先編譯，是靠瀏覽器裡的 Babel 即時翻譯的。所以第一次載入會比一般網站慢一兩秒。
- React、Firebase、圖示這些東西都是從網路上的 CDN 抓的（`esm.sh`、`unpkg.com`、`cdn.tailwindcss.com`、`www.gstatic.com`）。**完全離線打不開。** 網路只是慢的話沒關係，資料有本地快取。
- 因為要用 CDN 和即時編譯，`netlify.toml` 裡的內容安全政策（CSP）預設是關的，理由寫在那個檔案的註解裡。

### 檔案裡面長怎樣

打開 `index.html`，最上面 `<title>` 底下有一張**區塊地圖**，列出每個區塊的名字和行號。在編輯器裡搜 `// 【` 可以逐個跳過去。25 個區塊大致分成三層：

- **設定層**（檔案前段）：Firebase 設定、帳號模型、單位備用資料、版本記錄、Firestore 路徑、業務常數
- **邏輯層**（`App()` 內）：狀態宣告 → 資料訂閱 → 衍生計算 → 月報 → 管理員驗證 → 訂單編輯 → 列印 → 垃圾桶 → 人員狀態 → 圖片處理
- **畫面層**（檔案後段）：日期選擇、後台、點餐主頁、工坊選擇與登入頁、主框架

行號會隨著你的改動漂移，所以請以搜區塊名為準，不要照行號跳。

### 資料放在哪

全部在 Firestore，根路徑是 `artifacts/lunch-orders/public/data/`。（`lunch-orders` 這一段是 `index.html` 裡的 `appId` 常數，想改可以改，但 `firestore.rules` 裡的路徑要同步改成一樣，不然全部讀寫都會失敗。）

底下的結構：

| 路徑 | 放什麼 |
|---|---|
| `units/<單位id>` | 單位設定：名稱、顏色、地址、補貼金額、是否啟用 |
| `shops_shared` / `menu_shared` | 全部單位共用的店家與菜單 |
| `shops_<單位id>` / `menu_<單位id>` | 某個單位自己的店家與菜單 |
| `workshops/<單位id>/people` | 該單位的人員名單（姓名、身分別） |
| `workshops/<單位id>/orders` | 每日訂單，一人一筆 |
| `workshops/<單位id>/settings` | 三份文件：`schedule`（每日對應店家）、`today`（當日鎖定狀態）、`leave`（請假名單） |

## 誠實說明的限制

這一節寫的是這套系統做不到、或做得不夠好的地方。看完再決定要不要用。

### 管理員密碼是一道前端的門，不是資料層的鎖

系統有四種身分，但它們的職責不一樣：

| 身分 | 這個密碼實際上做什麼 |
|---|---|
| 單位帳號（`sunny@lunch.local`） | **真正的身分。** 資料寫進資料庫時用的就是這個身分，安全規則也是照它判斷 |
| 管理員（`admin@lunch.local`） | **前端的一道門。** 驗證通過就讓你看見管理畫面，驗完立刻登出，不留著 |
| 系統管理員（`sysadmin@lunch.local`） | 同上，但面板開著的期間會保持登入，因為要寫入單位設定 |

**規則層擋的是「跨單位讀寫」：陽光工坊的帳號碰不到河岸工坊的資料。** 但「管理員能改菜單、一般人不能」這件事，是靠前端那道門擋的。一個懂技術的人如果拿到某個單位的帳號密碼，是有辦法繞過那道門去改該單位資料的。

我們接受這個取捨，因為使用者是同一個場域裡的同事，而擋住「跨單位」才是真正要緊的那條線。如果你的情境裡，管理權限必須是真的擋得住的，那你要把權限判斷搬進 `firestore.rules`，而不是沿用這套。

### 測試站和正式站不要共用同一個 Firebase 專案

我們自己一開始就是共用的，結果是：在測試網址上點一筆假訂單，正式資料裡就真的多一筆。

**建議一開始就開兩個 Firebase 專案**（例如 `my-lunch` 和 `my-lunch-test`），各自有自己的六欄設定值，測試用的那份 `index.html` 貼測試專案的值。多花五分鐘，省掉之後每一次「這筆是真的還假的」的疑問。

### Firestore 的路徑有奇偶數規則

Firestore 的路徑是「集合／文件／集合／文件」交替的，集合永遠在奇數段、文件在偶數段。所以 `workshops/sunny/orders` 這種路徑是**合法的集合路徑**（三段），但 `workshops/sunny` 就是一份文件而不是集合。

自己拼路徑字串很容易數錯段數，錯了會得到看不懂的錯誤訊息。這份程式碼把路徑都收在 `unitsColPath()`、`workshopPath()` 這些函式裡（搜 `// 【Firestore 路徑】`），要加新資料表請沿用這個做法，不要在別處手拼字串。

### 網路設定為什麼寫成那樣

`index.html` 裡初始化 Firestore 的地方有兩個開關（搜 `initializeFirestore`）：

- `persistentLocalCache`：把資料存一份在瀏覽器本機。網路斷掉的時候畫面還看得到資料，恢復後自動同步。
- `experimentalAutoDetectLongPolling`：有些網路環境（校園、機構的內網、某些路由器）會擋住 Firestore 平常用的連線方式，開了這個之後 SDK 會自己偵測並改用相容性較好的方式。

兩個都是為了「在不理想的網路環境下還能用」而加的。**如果你在某個場地遇到「畫面一直轉圈、資料進不來」，先確認這兩行還在。**

順帶一提，本機快取是存在瀏覽器裡的，所以平板如果是多人共用，清除瀏覽器資料會把快取一起清掉（資料本身在雲端，不會遺失）。

### 密碼只能在 Firebase Console 改，系統裡沒有重設功能

沒有「忘記密碼」、沒有「修改密碼」畫面。要改就是負責人登入 Firebase Console → Authentication → Users → 找到那個帳號 → 重設密碼。

這是刻意的：做一個前端的改密碼功能，等於要讓前端有辦法動帳號，那反而多開一個口。小單位的帳號本來就少，交給 Console 管最單純。**代價是：Console 的登入權限一定要有人記得**，最好不只一個人知道。

### 其他已知的粗糙處

- 訂單照片是壓縮後以 base64 直接存進 Firestore 文件裡，單筆文件有 1MB 上限，照片太大會寫入失敗。
- 人員姓名是明文存放的，沒有加密。
- 沒有寫任何自動測試。改完請自己在瀏覽器點一遍。
- 只在 iPad Safari 與桌機 Chrome 上實際用過，其他瀏覽器沒測。
- 單位數量變多時，登入頁的卡片版面沒有特別處理過（大約超過六個會開始不好看）。
